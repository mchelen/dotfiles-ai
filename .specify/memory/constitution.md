# dotfiles-ai Constitution

dotfiles-ai is a set of personal preference modules for AI coding assistants and
the tooling that delivers them to every tool, machine, and project a person
works in. These principles are derived from what the codebase already enforces;
they are binding on changes to the modules, the scripts, the site, and the
workflows.

## Core Principles

### I. The modules are the source of truth

- `defaults/*.md` is the only place a preference is authored. Everything else —
  the block inside `~/.claude/CLAUDE.md`, `INSTRUCTIONS.md`, a block committed
  into a project's `CLAUDE.md`, text pasted into a settings field — is a
  **disposable copy**.
- A copy is never edited to change behavior. Edits go to `defaults/`, and the
  copy is regenerated or replaced.
- Anything generated from `defaults/` MUST be reproducible from it by running a
  command in this repo, with no manual step in between.

**Rationale:** The moment a copy becomes authoritative, every other copy is
silently wrong and there is no way to tell which one a given assistant read.

### II. Writes are idempotent and never destructive

- Generated content is delimited by the `BEGIN`/`END` markers. Everything
  outside them belongs to the user and MUST survive any number of re-runs
  byte-for-byte.
- Re-running an installer replaces the managed block in place. It MUST NOT
  duplicate, append a second block, or reorder unrelated content.
- A file that is about to be rewritten is backed up first.

**Rationale:** These files are ones people also write in by hand. A tool that
can lose that content is a tool people stop running.

### III. Opt in by detection, not by assumption

- A tool's instruction file is written only when that tool appears to be in use
  (its config directory exists), unless the operator explicitly overrides.
- Nothing is installed, enabled, or configured on a machine as a side effect of
  syncing.

**Rationale:** A dotfiles repo that scatters config for tools you don't use is
noise, and noise gets deleted.

### IV. Secret protection is layered and never disabled

- Three independent layers stay active: the pre-commit gitleaks hook, the same
  scan in CI, and GitHub's server-side push protection.
- A false positive is resolved with a targeted allow-marker, never by disabling
  a check or skipping a hook.
- Anything that reaches history is treated as compromised and rotated, not
  merely deleted.

**Rationale:** Any single layer can be bypassed — locally skipped, misconfigured
in CI, or absent on a fork. Three make a silent leak unlikely.

### V. Configuration and documentation are applied by CI, in the same change

- Repository settings live in Terraform under `infra/` and are applied by a
  workflow. Settings are not clicked through the web UI.
- `INSTRUCTIONS.md` is generated by a workflow, never hand-written.
- `ARCHITECTURE.md`, `README.md`, the site, and the specs under `specs/` are
  updated in the same pull request as the change that affects them — never as a
  later cleanup pass.

**Rationale:** Documentation and settings that are separately "due" are
documentation and settings that are wrong.

## Distribution Constraints

- **Fork-first.** Users are expected to fork, edit the modules, and point their
  machines at their own fork. Upstream reaches a fork only when its owner asks
  for it, through GitHub's *Sync fork*.
- **A no-terminal path must always exist.** Every capability that requires a
  shell needs a browser-only equivalent, or the cloud-agent and settings-UI
  users lose access to it.
- **No credentials in the delivery path.** The repo stays public and the
  install paths stay token-free; environment variables and setup scripts are
  not a secrets store.

## Development Workflow & Quality Gates

- Changes land through a pull request, merged when checks are green — never
  over a failing check, and never by rewriting history.
- Commits are small and focused; nothing is committed or pushed unless asked.
- Every behavioral change to a script updates the corresponding spec under
  `specs/` in the same pull request.

## Governance

This constitution supersedes ad-hoc practice. Amendments are made by pull
request, with the rationale recorded in the commit message; the version below
follows semantic versioning — MAJOR for removing or redefining a principle,
MINOR for adding one, PATCH for clarifications that do not change what is
allowed.

Compliance is reviewed at pull request time. A change that violates a principle
is either revised or accompanied by an explicit, recorded justification.
