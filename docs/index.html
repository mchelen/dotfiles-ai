dotfiles-ai.

Dotfiles, but for AI coding assistants — your personal working preferences, carried across every project and every tool.

Install See it in action View on GitHub

What it is

You have opinions about how an AI assistant should work with you: show me a mockup before you build the feature. Write the test first. Don't commit unless I ask. Today you re-explain those preferences in every session, or duplicate them into every project's instruction file.

dotfiles-ai keeps them in one place instead. Each preference is a small markdown module; an installer assembles the modules into the user-level instruction file of every AI tool on your machine — Claude Code, Codex, Copilot CLI, Gemini CLI, and friends — and a sync script keeps every machine current automatically.

Personal preferences live here, at the user level. Project conventions stay in each repo's own CLAUDE.md / AGENTS.md — this is the layer underneath.

The modules

Nine modules, grouped by the kind of behavior they govern. Each one is a short markdown file in defaults/<category>/ — read them, delete the ones you disagree with, add your own.

Collaboration — how the assistant works with you

communication

Lead with the answer, not the preamble. Say so when a request looks like a bad idea, before doing it. Disclose what was skipped, what's still failing, and what was left half-done — never present partial work as finished.

Without"I've completed the refactor and everything is working!"
(two tests were failing; you find out tomorrow)
With"Refactor is in. One caveat: checkout.spec.ts has two failures I didn't introduce and didn't fix — want me to take them next?"

feature-workflow

The flagship. For anything bigger than an obvious fix, the assistant owes you something to react to first — a mockup, a throwaway demo, two or three options with trade-offs, or a short written direction. Implementation waits for your nod. Small, unambiguous changes skip the ceremony.

Without400 lines land in the wrong architecture, and you review a finished thing you'd have designed differently.
With"Two approaches — client-side CSV, or a streaming endpoint. I'd pick the endpoint because reports exceed the page size. Sketch below. Which?"

Craft — how code gets written

code-style

The surrounding code wins over any general convention. Smallest change that solves the problem; no opportunistic refactors riding along in an unrelated diff. Comments explain non-obvious constraints, not what the line already says. New dependencies need a reason stated out loud.

WithoutAdds date-fns for one format call, reformats the whole file, and the real change is buried in a 300-line diff.
WithA six-line helper matching the file's existing style. Diff is six lines. No new dependency.

testing

Start from a failing test that captures the expected behavior, then write the code that makes it pass — and show both runs, so you can see the test actually exercises the change. Bug fixes begin with a reproduction. Tests target behavior, not internals.

Without"Fixed — should work now." No test proves it did, and nothing stops the bug returning next month.
WithFAIL parses timezone-less dates
PASS parses timezone-less dates
the bug now has a permanent guard

Delivery — how work ships

git

Nothing is committed or pushed unless you asked. Commits stay small and focused rather than bundling unrelated work. Once a branch is done it goes to a pull request automatically, gets watched, and merges itself when checks are green and reviews are in — but never over a failing check. History is never rewritten without asking.

WithoutOne commit titled "updates" touching 14 files, pushed straight to main, impossible to revert cleanly.
WithBranch → focused commits → PR opened → CI watched → squash-merged on green. You read a diff, not a mystery.

secrets

Three independent layers, because any one of them can be bypassed: the pre-commit framework running gitleaks locally, the same scan again in CI, and GitHub's server-side push protection. Checks are never quietly disabled — a false positive gets an inline allow-marker instead. Anything that reaches history is treated as compromised and rotated, not just deleted.

Without.env slips into a commit and is discovered a week later — by which point the key has been public in the history the whole time.
WithDetect hardcoded secrets……Failed
commit blocked before the key ever exists in history

repo-config

Repository settings — merge policy, Pages, security toggles, branch protection — live in Terraform under infra/ and get applied from CI, rather than being clicked through the web UI where they drift silently and nobody can review the change.

Without"Go to Settings → Advanced Security and turn on push protection." Undocumented, unreviewable, and gone if the repo is recreated.
WithA three-line change in infra/main.tf, reviewed in a PR, applied by CI on merge.

Documentation — what gets written down

architecture

Every project keeps an ARCHITECTURE.md at the root: major components, how they fit together, key data flows, with Mermaid diagrams. It's updated in the same change that rewires a component — never as a later cleanup pass. Deliberately high level, so small edits don't invalidate it.

WithoutThe diagram still shows a service that was deleted three months ago, so nobody trusts the doc and it decays further.
WithThe PR that adds the queue also updates the diagram. The doc is accurate because it's never separately "due".

project-website

Most projects get a static site explaining what it is, why it exists, and how to use it — including install steps for every environment where they differ, and a before/after demo of what the project actually changes. Where real screenshots aren't practical, simulate them and label them as simulated. This page is that module applied to itself.

WithoutA README that assumes you already know what the project does, and install steps that only cover the author's own setup.
WithThe page you're reading: what/why, per-environment install tabs, and a side-by-side demo.

How it works

1.Install once. install.sh concatenates the modules into a marker-delimited block and inserts it into each detected tool's user-level instruction file. Your own content in those files is never touched, and re-runs replace the block in place.

~/dotfiles-ai simulated output
$ ./install.sh
installed /Users/you/.claude/CLAUDE.md
installed /Users/you/.codex/AGENTS.md
installed /Users/you/.copilot/copilot-instructions.md
skipped  /Users/you/.qwen/QWEN.md (no ~/.qwen — tool not detected; use --all to force)

Done. For tools that only take rules through their settings UI
(e.g. Cursor "User Rules"), paste the output of:  ./install.sh --print

2.Stay in sync automatically. One line in your shell rc runs sync.sh --auto: at most once a day it pulls the latest main and re-installs — silent unless something actually changed. A versioned post-merge hook covers manual pulls too.

new terminal, next morning simulated output
# ~/.zshrc: [ -x "$HOME/dotfiles-ai/sync.sh" ] && "$HOME/dotfiles-ai/sync.sh" --auto
dotfiles-ai: updated d78d121 -> cae0439
updated  /Users/you/.claude/CLAUDE.md (previous version saved to ….bak)
updated  /Users/you/.codex/AGENTS.md (previous version saved to ….bak)
$ ▍

3.Evolve by pull request. Notice a new preference mid-session? Add a module on any machine, merge it, and every other machine picks it up on its next shell start.

Built-in guardrails

The repo practices its own defaults on itself:

Leak protection, three layers

The standard pre-commit framework runs the official gitleaks hook (plus private-key and AWS-credential detectors) on every commit, with PII rules for SSN and card numbers extending gitleaks' defaults. The same scan runs again in GitHub Actions on every push and PR, and GitHub's server-side secret scanning with push protection backstops both.

Repo settings as code

Description, merge policy, Pages, and security toggles are declared in Terraform (official GitHub provider) — never clicked through the web UI. A CI workflow re-applies the config whenever it changes on main, using a stateless import pattern with no backend to manage.

Docs that keep up

An ARCHITECTURE.md with Mermaid diagrams, this site, and the README all update in the same pull request as the change that affects them — per the architecture and project-website modules.

Install

Steps differ by where the assistant runs. Pick your setup:

Covers Claude Code (CLI, desktop app, IDE extensions), Codex CLI, Copilot CLI, Gemini CLI, Qwen Code, OpenCode, and Goose — anything that reads a user-level instruction file. The installer writes to every tool it detects, so one run covers all of them.

1.Clone and install

~ simulated output
$ git clone https://github.com/mchelen/dotfiles-ai ~/dotfiles-ai
$ ~/dotfiles-ai/install.sh
installed /Users/you/.claude/CLAUDE.md
installed /Users/you/.codex/AGENTS.md
installed /Users/you/.copilot/copilot-instructions.md
skipped  /Users/you/.qwen/QWEN.md (no ~/.qwen — tool not detected; use --all to force)

2.Keep it current

One line in your shell rc re-syncs at most once a day, silently unless something changed:

~/.zshrc simulated output
$ echo '[ -x "$HOME/dotfiles-ai/sync.sh" ] && "$HOME/dotfiles-ai/sync.sh" --auto' >> ~/.zshrc
# optional — enables the secret-scanning commit hooks:
$ pipx install pre-commit

3.Verify

Start a new session and ask for a feature. If the assistant proposes options before writing code, it's live.

Why this differs: a cloud session runs in a fresh container that clones your repo — it never sees ~/.claude/CLAUDE.md on your laptop. The defaults have to travel inside the repo, so you commit them to the project's own CLAUDE.md.

1.Append the block to the project's CLAUDE.md

~/code/your-project simulated output
$ ~/dotfiles-ai/install.sh --print >> CLAUDE.md
$ git add CLAUDE.md && git commit -m "Add AI assistant defaults"
$ git push

The block is marker-delimited, so re-running the command later replaces it cleanly instead of duplicating it. Remember this file is shared with collaborators — drop any module you wouldn't impose on the team.

2.Start a session

Open claude.ai/code, pick the repo, and the defaults load with the checkout — no per-session setup:
