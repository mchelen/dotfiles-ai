Quick start

Want the defaults working right now, in a session you already have open? Paste this in. It works in Claude Code — terminal, desktop, or claude.ai/code — and in any other assistant that can read a URL.

Read https://raw.githubusercontent.com/mchelen/dotfiles-ai/main/INSTRUCTIONS.md
and follow it for the rest of this session — those are my working defaults.

Then tell me briefly how to keep them, and offer to set up whichever I pick:
  - this project only: commit the block into CLAUDE.md (or AGENTS.md)
  - every session: fork the repo, then run install.sh on my machine, or add it
    to my Claude Code environment setup script

If I later want to change a preference, remind me it lives in defaults/ in my
fork — the copy you just read is disposable.

What that does

  1. Immediately: the assistant reads INSTRUCTIONS.md — every module, already assembled — and follows it for this session. Nothing is installed, nothing is committed, and it works in a session that's already running.
  2. Then: it explains the two ways to make that permanent and offers to do the work, so you don't have to come back here and read the install guide.
  3. Later: it knows to send you to defaults/ in your own fork when you want to change something — never to the pasted copy, which is disposable by design.

Fetching needs network access. In a claude.ai/code session, raw.githubusercontent.com is on the default Trusted allowlist, so it works as-is. If your tool can't reach the internet, open INSTRUCTIONS.md, click Copy raw file, and paste the block itself instead.

This is the zero-commitment version — it lasts one session and uses this repo's opinions. When you want them on every machine and every project, and edited to your taste, start at Install, which begins by forking.

What it is

You have opinions about how an AI assistant should work with you: show me a mockup before you build the feature. Write the test first. Don't commit unless I ask. Today you re-explain those preferences in every session, or duplicate them into every project's instruction file.

dotfiles-ai keeps them in one place instead. Each preference is a small markdown module; an installer assembles the modules into the user-level instruction file of every AI tool on your machine — Claude Code, Codex, Copilot CLI, Gemini CLI, and friends — and a sync script keeps every machine current automatically.

Personal preferences live here, at the user level. Project conventions stay in each repo's own CLAUDE.md / AGENTS.md — this is the layer underneath.

The modules

Twelve modules, grouped here by the kind of behavior they govern. Each one is a short markdown file in defaults/ — read them, delete the ones you disagree with, add your own.

Collaboration — how the assistant works with you

communication

Lead with the answer, not the preamble. Say so when a request looks like a bad idea, before doing it. Disclose what was skipped, what's still failing, and what was left half-done — never present partial work as finished.

Without"I've completed the refactor and everything is working!"
(two tests were failing; you find out tomorrow)
With"Refactor is in. One caveat: checkout.spec.ts has two failures I didn't introduce and didn't fix — want me to take them next?"

feature-workflow

The flagship. For anything bigger than an obvious fix, the assistant owes you something to react to first — a mockup, a throwaway demo, two or three options with trade-offs, or a short written direction. Implementation waits for your nod. Small, unambiguous changes skip the ceremony.

Without400 lines land in the wrong architecture, and you review a finished thing you'd have designed differently.
With"Two approaches — client-side CSV, or a streaming endpoint. I'd pick the endpoint because reports exceed the page size. Sketch below. Which?"

tool-fallbacks

Tooling fails sometimes. When an interactive prompt looks stuck — the same card reappearing, or you saying you answered something that never arrived — the assistant drops to plain text rather than retrying the thing that just broke. A reported refusal is treated as possibly-lost input, not a decision, because retrying through a broken mechanism is exactly what turns one lost answer into a loop. Written after this bug: a dismissed question card silently discards typed text.

WithoutThe card is re-issued after every failure. You answer the same question four times and nothing moves forward.
With"That came back as a decline, but you said you answered — the card is probably eating input. Switching to plain text: <question>"

compute-offload

Mechanical work goes to a command, not into the context window: query with grep, jq, and diff instead of reading a large file to find a small part of it; make verification scripts print a verdict rather than a transcript; put a check that must hold every time into CI. With guardrails, because the cheap path isn't always the right one — judgment doesn't offload, a fragile parser written to avoid a short read is a bad trade, and a filtered or partial check is always disclosed as one.

WithoutA 345 KB API response is pulled into context to learn which three CI jobs ran. The answer arrives, and the room for the actual task doesn't.
Withjq -r '.runs[] | "\(.name) \(.conclusion)"'
eight lines, same answer, re-runnable next time

Craft — how code gets written

code-style

The surrounding code wins over any general convention. Smallest change that solves the problem; no opportunistic refactors riding along in an unrelated diff. Comments explain non-obvious constraints, not what the line already says. New dependencies need a reason stated out loud.

WithoutAdds date-fns for one format call, reformats the whole file, and the real change is buried in a 300-line diff.
WithA six-line helper matching the file's existing style. Diff is six lines. No new dependency.

testing

Start from a failing test that captures the expected behavior, then write the code that makes it pass — and show both runs, so you can see the test actually exercises the change. Bug fixes begin with a reproduction. Tests target behavior, not internals.

Without"Fixed — should work now." No test proves it did, and nothing stops the bug returning next month.
WithFAIL parses timezone-less dates
PASS parses timezone-less dates
the bug now has a permanent guard

Delivery — how work ships

git

Nothing is committed or pushed unless you asked. Commits stay small and focused rather than bundling unrelated work. Once a branch is done it goes to a pull request automatically, gets watched, and merges itself when checks are green and reviews are in — but never over a failing check. History is never rewritten without asking.

WithoutOne commit titled "updates" touching 14 files, pushed straight to main, impossible to revert cleanly.
WithBranch → focused commits → PR opened → CI watched → squash-merged on green. You read a diff, not a mystery.

secrets

Three independent layers, because any one of them can be bypassed: the pre-commit framework running gitleaks locally, the same scan again in CI, and GitHub's server-side push protection. Checks are never quietly disabled — a false positive gets an inline allow-marker instead. Anything that reaches history is treated as compromised and rotated, not just deleted.

Without.env slips into a commit and is discovered a week later — by which point the key has been public in the history the whole time.
WithDetect hardcoded secrets……Failed
commit blocked before the key ever exists in history

repo-config

Repository settings — merge policy, Pages, security toggles, branch protection — live in Terraform under infra/ and get applied from CI, rather than being clicked through the web UI where they drift silently and nobody can review the change.

Without"Go to Settings → Advanced Security and turn on push protection." Undocumented, unreviewable, and gone if the repo is recreated.
WithA three-line change in infra/main.tf, reviewed in a PR, applied by CI on merge.

Documentation — what gets written down

architecture

Every project keeps an ARCHITECTURE.md at the root: major components, how they fit together, key data flows, with Mermaid diagrams. It's updated in the same change that rewires a component — never as a later cleanup pass. Deliberately high level, so small edits don't invalidate it.

WithoutThe diagram still shows a service that was deleted three months ago, so nobody trusts the doc and it decays further.
WithThe PR that adds the queue also updates the diagram. The doc is accurate because it's never separately "due".

specification

Intended behavior gets written down in the repo, in a standard format — currently Spec Kit: a spec.md per feature under specs/, with plan.md and tasks.md derived from it. The spec says what and why; the plan says how. When intended behavior changes the spec is revised in the same change as the code, and code that contradicts the spec gets raised as a question rather than silently resolved in either direction.

Without"What is this supposed to do?" is answered by reading the implementation — so whatever the code does becomes the definition of correct, bugs included.
With"spec.md says expired invites are rejected; the handler renews them. Which is right?" — a contradiction surfaces as a decision instead of a silent drift.

project-website

Most projects get a static site explaining what it is, why it exists, and how to use it — including install steps for every environment where they differ, and a before/after demo of what the project actually changes. Where real screenshots aren't practical, simulate them and label them as simulated. This page is that module applied to itself.

WithoutA README that assumes you already know what the project does, and install steps that only cover the author's own setup.
WithThe page you're reading: what/why, per-environment install tabs, and a side-by-side demo.

How it works

1.Fork, then install once. You start by forking, because the modules are meant to be edited and every copy should follow a repo you control. Then install.sh concatenates the modules into a marker-delimited block and inserts it into each detected tool's user-level instruction file. Your own content in those files is never touched, and re-runs replace the block in place.

~/dotfiles-ai simulated output
$ ./install.sh
installed /Users/you/.claude/CLAUDE.md
installed /Users/you/.codex/AGENTS.md
installed /Users/you/.copilot/copilot-instructions.md
skipped  /Users/you/.qwen/QWEN.md (no ~/.qwen — tool not detected; use --all to force)

Done. For tools that only take rules through their settings UI
(e.g. Cursor "User Rules"), paste the output of:  ./install.sh --print

2.Stay in sync automatically. One line in your shell rc runs sync.sh --auto: at most once a day it pulls the latest main and re-installs — silent unless something actually changed. A versioned post-merge hook covers manual pulls too.

new terminal, next morning simulated output
# ~/.zshrc: [ -x "$HOME/dotfiles-ai/sync.sh" ] && "$HOME/dotfiles-ai/sync.sh" --auto
dotfiles-ai: updated d78d121 -> cae0439
updated  /Users/you/.claude/CLAUDE.md (previous version saved to ….bak)
updated  /Users/you/.codex/AGENTS.md (previous version saved to ….bak)
$ ▍

3.Evolve by pull request. Notice a new preference mid-session? Add a module on any machine, merge it, and every other machine picks it up on its next shell start.

Built-in guardrails

The repo practices its own defaults on itself:

Leak protection, three layers

The standard pre-commit framework runs the official gitleaks hook (plus private-key and AWS-credential detectors) on every commit, with PII rules for SSN and card numbers extending gitleaks' defaults. The same scan runs again in GitHub Actions on every push and PR, and GitHub's server-side secret scanning with push protection backstops both.

Repo settings as code

Description, merge policy, Pages, and security toggles are declared in Terraform (official GitHub provider) — never clicked through the web UI. A CI workflow re-applies the config whenever it changes on main, using a stateless import pattern with no backend to manage.

Docs that keep up

An ARCHITECTURE.md with Mermaid diagrams, this site, and the README all update in the same pull request as the change that affects them — per the architecture and project-website modules.

Install

Every path starts the same way — fork the repo (steps 1–3). After that the steps differ by where your assistant runs; pick the tab that matches and continue at step 4.

Step 0 · Fork it — everyone, whichever path you take

Why a fork, and not this repo?

  • These are one person's preferences, and you're expected to edit them. Every module here is an opinion — "propose before you build", "test first", "never commit unless asked". Some will fit you, some won't. Deleting a module you disagree with and adding three of your own is the normal way to use this project, and that means writing to a repo you own.
  • Your machines should sync from a repo you control. Both sync.sh and the copy-paste flow below pull from whatever repo you point them at. Point them upstream and someone else's edits land on your machines unannounced; point them at your fork and you decide what arrives, and when, by clicking Sync fork.

9.Make them yours

Edit files in ~/dotfiles-ai/defaults/, then git push to your fork and re-run install.sh. Every other machine picks the change up on its next shell start.

Configure once, and every future cloud session has the defaults — in every repo you open. Nothing is committed to any project, so teammates are unaffected. This is the closest thing to the local install if you work mostly on the web.

A cloud session runs in a fresh VM. Its environment can carry a setup script: a Bash script that runs as root before Claude Code launches, and whatever it writes to disk stays. So the script clones your fork and runs install.sh — exactly what you'd do on a laptop — leaving the block in the container's ~/.claude/CLAUDE.md. (Claude Code's docs list your laptop's ~/.claude/CLAUDE.md as not available in a cloud session, because it lives on your machine rather than in the repo. The setup script recreates it inside the container instead.)

Pick the one project tab instead when the defaults should apply to a specific repo for everyone who works on it, including collaborators and other cloud agents.

9.To pick up module edits, bump the script

The setup script's result is snapshot-cached — it runs on the first session in an environment, then later sessions start from that saved filesystem. It re-runs only when you change the script, change the allowed hosts, or after roughly seven days. Editing a comment in the script is enough to force a rebuild after you change defaults/.

Worth knowing:

  • Keep the dotfiles repo public. A private fork would need a token in the clone URL, and environment variables are not a secrets store. These are preferences, not secrets.
  • Network access must not be None. github.com is on the default Trusted allowlist, so the clone works with no extra configuration.
  • Teams: owners and admins on Team and Enterprise plans can put the same script in an organization-shared environment (admin settings → Cloud environments), so everyone's sessions start with an agreed baseline.
  • Always-fresh alternative: a SessionStart hook in a repo's .claude/settings.json runs on every session including resumes, cloud and local — no cache to bust — but it's committed to that repo, so it's per-project and your collaborators run it too.

Use this when the defaults should belong to one repo — applying to collaborators and to any cloud agent that opens it. To set yourself up once for every repo instead, see the every session tab.

Why this differs: a cloud session runs in a fresh container that clones your repo — it never sees ~/.claude/CLAUDE.md on your laptop. The defaults have to travel inside the repo, so they go into the project's own AGENTS.md.

No terminal, no clone, nothing installed. Every step below happens in the browser. That works because your fork carries a generated file at its root, INSTRUCTIONS.md — every module in defaults/, already assembled into one marker-delimited block, ready to copy. A GitHub Actions workflow regenerates it on every change to defaults/ on main, so it is current even when you edit modules from the web editor.

7.Open (or create) that repo's AGENTS.md

If it already exists, click it in the file list. If it doesn't: Add file ▾ → Create new file, then type AGENTS.md as the filename — that drops you straight into the editor, so skip step 8.

Why AGENTS.md and not CLAUDE.md? AGENTS.md is the cross-tool convention — a community specification stewarded by the Agentic AI Foundation under the Linux Foundation since December 2025, read by roughly fifteen agents including Codex, Cursor, Copilot, Gemini CLI, Windsurf, Aider, Zed and Amazon Q. One file, most tools.

Claude Code is the exception, and it needs one extra step. Its documentation is explicit that it reads CLAUDE.md and not AGENTS.md. The documented fix is a one-line CLAUDE.md that imports the other file, so both read the same block with nothing duplicated — that's step 12 below.

12.Add a CLAUDE.md that imports it

This is the step that makes Claude Code see the block, since it doesn't read AGENTS.md. Repeat steps 7–11 for a file named CLAUDE.md, but instead of pasting the block, its entire contents are one line:

CLAUDE.md paste, don't run
@AGENTS.md

Claude Code expands that import at session start, so both files stay in sync with no duplication — and future refreshes only ever touch AGENTS.md. Anything you want Claude Code to do and not the other agents can go below the import line.

From a clone you could symlink instead — ln -s AGENTS.md CLAUDE.md — but the import is the better default here: it works on Windows without Developer Mode, and it leaves room for Claude-specific additions.

Your machines ← your fork — sync.sh

Installed blocks are copies; they only change when install.sh runs. Two things run it for you:

1.Shell startup. The line added in the local install path runs sync.sh --auto: at most once a day it fast-forwards your fork's main and re-installs. It is silent when there's nothing new, when you're offline, or when throttled.

2.Manual pulls. A post-merge hook (pre-commit framework) re-runs install.sh after any git pull in the clone, so the installed files never lag the checkout.

Cloud sessions ← your fork — the environment setup script

The setup script clones your fork, so each run picks up whatever main holds at that moment — but the run itself is snapshot-cached, not repeated per session. New sessions start from the saved filesystem until the cache rebuilds, which happens when you change the script, change the environment's allowed hosts, or after roughly seven days.

So: edits to defaults/ reach your cloud sessions within a week on their own, or immediately if you open the environment settings and change one character in the script. Resuming an existing session never re-runs it.

Project repos ← your fork — manual refresh of a committed block

A block committed into some project's AGENTS.md or CLAUDE.md is a snapshot in that repo's history. Nothing updates it on its own — and deliberately so: those files are shared with collaborators, and a bot rewriting them under a team is a worse default than doing it when you mean to. There's no upstream-sync bot for this today. To refresh one:

1.Open INSTRUCTIONS.md in your fork and click Copy raw file.

2.Open the project's AGENTS.md (or CLAUDE.md) and click the pencil icon.

3.Select from the <!-- BEGIN dotfiles-ai … --> line through the <!-- END dotfiles-ai --> line, inclusive, and delete it.

4.Paste the fresh block in its place.

5.Click Commit changes… → Commit changes.

The markers are what make this safe: everything outside them — the project's own instructions — is untouched. Same procedure from a clone if you prefer: ~/dotfiles-ai/install.sh --print, then swap the block.
